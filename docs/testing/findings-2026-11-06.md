# Verity API test report

> Historical observations against `cb8915c`, supplied with the original test materials.
> These findings are not a claim about the current release. See [fix tracking and required native retests](README.md#findings-and-retests).

**Test date:** 6 November 2026\
**Source:** https://github.com/pgodlews/verity-api, main at `cb8915c` (source ZIP)\
**Platform:** macOS 27.2, Apple silicon; Apple Command Line Tools, Go 1.26.10 and 1.27.3, Node 24.11.1

## Finding 1 — aliased paths break Git safeguards and project recognition

**Severity:** High, because a test demonstrates that a staged secret can be committed.\
**Status:** Reproduced by the project's own tests on this Mac.

With the default macOS temporary directory under `/var/folders/...` (where `/var` resolves to `/private/var`), the workspace mixes aliased and resolved paths. Git changes are reported as paths containing many `../` components and marked `ProjectFile:false`. In the same configuration, the test `TestCommitScansStagedSecrets` reports `staged secret was committed`, and `TestHookLifecycle` reports `config_error: hook project must be inside the git repository`. Other tests also report a dirty project being switched and failures to identify metadata/watch paths. The test suite indicates these are multiple effects of path handling; the common cause should be confirmed during repair.

**Reproduce:** from the repository root, with Git available, run:

```sh
go test ./core/workspace -run 'TestCommitScansStagedSecrets|TestHookLifecycle|TestGitChangesInRepo' -count=1
```

On this Mac, all three named tests failed using the default `TMPDIR`. The same selected tests passed when `TMPDIR` was set to a real workspace directory with no `/var` symlink alias. This comparison limits the finding to paths with equivalent aliased/resolved forms; it does not establish that every macOS project is affected. The tests use disposable test secrets and repositories; no real credential was exposed. Investigate consistent canonicalization before computing paths, identifying project files, installing hooks, and applying staged-secret and dirty-file safeguards.

## Finding 2 — desktop build compatibility observations

**Status:** Environment-specific; a general product defect is not confirmed. See the follow-up below.

With Wails 2.12.0, Go 1.26.10, Node 24.11.1 and the installed Apple Command Line Tools, the documented `cd gui && wails build` failed at application compilation. A direct `go build -tags production` gave the concrete linker error `Undefined symbols for architecture arm64: _OBJC_CLASS_$_UTType`. A direct binary build succeeded after setting `CGO_LDFLAGS='-framework UniformTypeIdentifiers'`, but the Wails packaging command still failed in this environment. With Go 1.27.3 the Wails binding generation also failed with `package "context" without types`; the documented prerequisite says Go 1.26+.

At this initial stage, the resulting standalone binary launched but a usable native window could not be confirmed. Subsequent follow-ups below document the successful Wails package, native UI testing, and published-release smoke test.

## Follow-up — native Wails build (6 November 2026)

After the execution environment's permissions changed, Wails 2.12.0 successfully built and self-signed the native macOS application using Go 1.26.10 and `CGO_LDFLAGS='-framework UniformTypeIdentifiers'`. The app launched and appeared as a running macOS application. This supersedes the earlier statement that Wails packaging could not be completed: the earlier packaging failure occurred under the restricted execution environment and cannot be attributed to the project on its own. The unmodified linker failure and Go 1.27 binding-generation error remain observed, but their generality has not been established.

At that stage, computer control was denied access to Verity. Access was subsequently restored and the native UI was tested, as described below and in the Apple-silicon follow-up report.

## Finding 3 — invalid load-test settings discard the previous report

**Severity:** Medium (loss of unsaved results).\
**Status:** Reproduced in the native Wails app using computer control.

1. Open the bundled local demo with its fixture server running, select **Load test**, select the REST suite, and run with one virtual user for one second.
2. Observe the successful report and **Save JSON report** button.
3. Set **Virtual users** to `0` and select **Start load test**.
4. The app correctly reports that virtual users must be between 1 and 1000, but it also removes the previous report and its save button, replacing the results with **No load report yet**. No new run was started, and the previous unsaved result is no longer available in the view.

The handler calls `onClearReport()` before checking `currentOptions` in `gui/frontend/src/views/LoadView.tsx`; validation should complete before the previous report is discarded. Other preflight rejections using that handler may have the same effect, but were not individually tested.

## Follow-up — native UI testing completed (6 November 2026)

Following a reboot and app approval, computer control successfully operated the native Wails application. The sample project opened through the macOS file picker. The REST request returned HTTP 200 and passed 4/4 checks; the SOAP request returned HTTP 200 and passed 2/2 checks. The bundled OpenAPI file previewed as three requests with no warnings. Running the collection with no demo token gave the expected secured-request HTTP 401 failure while REST and SOAP passed. A one-second, one-user REST load test passed on the local fixture with zero failed requests, after which the invalid-input report-loss issue above was reproduced. These observations supersede the earlier statement that no native UI testing was performed; they do not imply comprehensive coverage of all desktop workflows.

## Source verification follow-up

- **Load report loss confirmed:** `gui/frontend/src/views/LoadView.tsx:163` invokes `onClearReport()` before checking `currentOptions` and before the threshold and target checks. `gui/frontend/src/App.tsx:341` supplies a callback that sets the stored `lastLoad` to `null`. Consequently a rejected start removes the report and the UI can no longer save it. The invalid virtual-user case was reproduced through the native UI; other rejection paths are source-derived and were not individually reproduced.
- **Git secret-scan bypass confirmed with an independent disposable repository:** `core/workspace/staged.go:150–155` compares project file paths from `projectFileSet` against paths joined to Git's repository root without resolving both representations consistently. When the project path uses `/var/...` while Git returns `/private/var/...`, the selected project file is skipped by the scan. `core/workspace/gitops.go:118–128` then proceeds to commit when the scan is clean. An independent diagnostic using a disposable repository and a fake credential confirmed that `Commit` returned success and `git show HEAD:project.yaml` contained the fake credential. This confirms the actual committed content, beyond the failing test's error message. Never use real credentials for reproduction.
- **Hook refusal confirmed in source:** `core/workspace/hooks.go:26–46` calculates a relative path between Git's root and the project path without first resolving both; equivalent `/var` and `/private/var` paths can therefore be treated as outside the repository. The existing hook lifecycle test reproduced the refusal.
- **Build issue classification:** the original Wails packaging failure is not confirmed as a product bug because the subsequent Wails build succeeded outside the restricted environment. The Go 1.27 and linker observations remain environment-specific; no general compatibility claim is established.

## Finding 4 — saving a request changes an unrelated folded YAML description

**Severity:** Medium (unintended modification of project data).\
**Status:** Reproduced in the native Wails UI and verified by decoding both versions of the file.

Open a clean Git-tracked copy of `examples/local-demo/project.yaml`, change the REST `fetch` URL from `${BASE_URL}/json` to `${BASE_URL}/json?ui_test=1`, and save the request. The source-control view shows the requested URL change **and** a project description change. Comparing the parsed YAML strings before and after shows that the save inserts extra blank lines in the unrelated description. The raw diff also rewrites formatting elsewhere.

`core/workspace/savestep.go:220–247` parses a YAML node, replaces the step and calls `yaml.Marshal` on the entire document before passing it to `model.FormatYAML`. A diagnostic confirmed that this initial `yaml.Marshal` alone changes the decoded description; the subsequent formatter cannot recover the original value. `core/workspace/saveenv.go:224` also uses `formatEditedYAML`, but this specific environment-edit path was not independently reproduced. Preserve semantic values and add regression tests for folded scalars, especially text with indented lines, across request and environment saves.

## Finding 5 — newly modified project files are not preselected in source control

**Severity:** Low (unexpected extra step, documented default not met).\
**Status:** Reproduced in the native Wails UI and checked against source.

1. Open a clean Git-tracked project in Verity and let its status load.
2. Edit and save a request, then open **Source control**. The modified `project.yaml` appears unchecked, despite the desktop guide saying project files start checked.
3. Close the project and reopen the same already-modified project. The same `project.yaml` now appears checked.

`gui/frontend/src/views/SourceControl.tsx:83–90` stores the first reconciled selection, including `[]` when no files are changed. `gui/frontend/src/lib/gitops.ts:32–35` subsequently keeps only previously selected paths and never adds newly appearing project files, even when the user made no selection. An initial clean status therefore becomes indistinguishable from an explicit user choice to select nothing. A fix should preserve deliberate unchecking while providing the intended default for newly appearing project files; the existing helper tests explicitly preserve `[]`, so integration coverage must distinguish these cases.
